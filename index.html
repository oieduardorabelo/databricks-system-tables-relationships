Databricks system tables: how they connect

Databricks keeps operational data about your account in system tables. These tables record billing, compute, jobs, queries, access events and more. Databricks fills them automatically. You read them with SQL, for example to find cost or to audit access.

This page shows how the tables connect. Each box is a table. Each line connects a column in one table to a column in another table. You use these lines to write joins. A join is a SQL step that combines rows from two tables when their column values match.

Terms

Account
Your top-level Databricks organisation. One account can have many workspaces.
Workspace
An environment where users run notebooks, jobs and queries. Each workspace is in one cloud region, for example us-west-2.
Unity Catalog
The Databricks governance layer. It controls who can read which data.
Metastore
The top-level Unity Catalog container for one region. Each workspace connects to the metastore of its region.
Catalog, schema and table
A catalog contains schemas. A schema contains tables. The full table name has three parts: catalog.schema.table. For example, system.billing.usage is the usage table in the billing schema of the system catalog.
Primary key
The column, or set of columns, that identifies one row. The diagram underlines primary key columns.
Struct
A column that contains named fields. You read a field with a dot, for example usage_metadata.warehouse_id. The diagram shows struct fields with a bullet (•).
SQL warehouse
A compute resource that runs SQL queries.
Cardinality
How many rows on each side of a line can match. The symbols at the line ends show it. The legend under the diagram explains each symbol.

Key join paths

Start with these four joins. They connect cost, warehouses, workspaces and queries. Click a path to show it in the diagram.

    Account scope and region scope

    Scope tells you which workspaces a table includes. If you ignore scope, your query can miss data or give wrong totals.

    Databricks account
    • Metastore: us-west-2
      • system.billing.usageglobal: all regions
      • system.compute.warehousesregional: us-west-2 only
      • system.query.historyregional: us-west-2 only
    • Metastore: eu-west-1
      • system.billing.usageglobal: all regions
      • system.compute.warehousesregional: eu-west-1 only
      • system.query.historyregional: eu-west-1 only

    A global table contains data from all workspaces in all regions of the account. You get the same data from any metastore. Global tables include system.billing.usage, system.billing.list_prices and system.access.workspaces_latest.

    A regional table contains data only from workspaces in the region of the metastore that you query from. Regional tables include system.compute.warehouses, system.compute.warehouse_events, system.query.history and system.access.audit. The audit table has workspace-level events only.

    Example. Your account has workspaces in us-west-2 and eu-west-1.

    1. You query system.billing.usage from a workspace in us-west-2. You get cost rows for both regions.
    2. You query system.compute.warehouses from the same workspace. You get warehouses in us-west-2 only.
    3. You join the two tables on the warehouse ID. The eu-west-1 cost rows have no matching warehouse, so an inner join drops them. Your total cost is too low.

    Best practices for queries

    RuleWhy and how
    ✅ Filter on a date column firstSystem tables can contain many months of data. Add a date filter, for example WHERE usage_date >= ... or WHERE event_time >= .... Put the filter before you aggregate. This stops a full table scan, which reads every row.
    ✅ Filter usage to SQL warehousessystem.billing.usage has rows for all Databricks products. To analyse SQL warehouse cost only, add WHERE billing_origin_product = 'SQL'.
    ✅ Get the current warehouse configurationsystem.compute.warehouses adds a new row for each configuration change. This design is a slowly changing dimension. To get one current row for each warehouse, use WHERE delete_time IS NULL with QUALIFY ROW_NUMBER() OVER (PARTITION BY warehouse_id ORDER BY change_time DESC) = 1.
    ✅ Use SUM to include billing correctionsDatabricks can correct usage rows later. A RETRACTION row has a negative quantity that cancels the original row. A RESTATEMENT row has the corrected quantity. Always aggregate with SUM(usage_quantity), so the corrections cancel out correctly.
    ✅ Use dot notation for struct fieldsWrite the full path to the field in the join, for example u.usage_metadata.warehouse_id = w.warehouse_id.
    ✅ Set skipChangeCommits = true when you streamA stream reads new rows from a table continuously. Databricks sometimes deletes rows from system tables, and these deletes can stop the stream with an error. This option tells the stream to ignore deletes and updates.

    Summary

    • System tables are in the system catalog. Unity Catalog controls access to them. You can read them, but you cannot change them.
    • Global tables, such as system.billing.usage and system.billing.list_prices, contain data from all regions. Regional tables, such as system.compute.* and system.query.history, contain data from the region of the current metastore only.
    • For cost and usage analysis, start with four schemas: billing, compute, query and access.
    • To read system tables, your workspace must use Unity Catalog. Account admins can read them by default. Other users need a grant, which is a permission that an admin gives.
    • Filter on a date column first. Use billing_origin_product = 'SQL' to isolate SQL warehouse cost. Use SUM(usage_quantity) to include billing corrections.
