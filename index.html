Databricks system tables: how they connect

Databricks records what happens in your account in system tables. You read these tables with SQL to find cost, check usage and audit access.

The tables cover billing, compute, jobs, queries, access events and more. Databricks fills them automatically. You cannot change them.

The diagram shows how the tables connect, so that you can write joins between them. A join is a SQL step that combines rows from two tables when their column values match.

How to read the diagram

Boxes
Each box is a table. It shows its key columns first: the columns that identify a row or join to another table. Click + more columns to see every column. Click a table, a column or a line to see its joins, with SQL that you can copy.
Lines
Each line joins a column in one table to a column in another table. The symbol at each end shows how many rows can match: a bar means exactly one, a crow's foot means many, and a circle with a crow's foot means zero or many.
Underlined column
The column is part of the primary key: the column, or set of columns, that identifies one row.
Bullet (•)
The row is a field inside a struct column. Read it with a dot, for example usage_metadata.warehouse_id.
Scope badge
global tables contain data from all regions of the account. regional tables contain data from one region only. Account scope and region scope explains why this matters.
Status badge
A table without a status badge is generally available. preview means Public Preview: Databricks can still change the table. beta is an early release that Databricks can change or remove. unlisted means the table exists, but the Databricks documentation does not describe it yet.

What the diagram covers

The diagram covers every system table: 58 tables in 18 schemas of the system catalog.

  • It leaves out system.information_schema. That schema describes your data objects, such as catalogs, tables and privileges, not account activity.
  • Your account can show fewer tables. A system schema appears only after an admin enables it, or when you use its feature.

Key join paths

Start with these four joins. Together, they connect cost to warehouses, workspaces and queries. Click a path to show it in the diagram.

    Account scope and region scope

    Scope tells you which workspaces a table includes. It depends on the metastore: the top-level Unity Catalog container for one region. Each workspace connects to the metastore of its region. If you ignore scope, your query can miss data or give wrong totals.

    A global table contains data from all workspaces in all regions of the account. You get the same data from any metastore. Global tables include system.billing.usage, system.billing.list_prices and system.access.workspaces_latest.

    A regional table contains data only from workspaces in the region of the metastore that you query from. Regional tables include system.compute.warehouses, system.compute.warehouse_events, system.query.history and most other tables. In system.access.audit, workspace-level events are regional and account-level events are global.

    Each box in the diagram shows the scope of its table.

    Example: a join that loses cost

    Your account has workspaces in us-west-2 and eu-west-1.

    1. You query system.billing.usage from a workspace in us-west-2. You get cost rows for both regions.
    2. You query system.compute.warehouses from the same workspace. You get warehouses in us-west-2 only.
    3. You join the two tables on the warehouse ID. The eu-west-1 cost rows have no matching warehouse, so an inner join drops them.

    The result: your total cost is too low, and the query shows no error.

    Best practices for queries

    Each rule makes queries faster, cheaper or more correct.

    RuleWhy and how
    Filter on a date column firstSystem tables can contain many months of data. Add a date filter, for example WHERE usage_date >= ... or WHERE event_time >= .... Put the filter before you aggregate. Without it, the query reads every row in the table.
    Filter usage to SQL warehousessystem.billing.usage has rows for all Databricks products. To analyse SQL warehouse cost only, add WHERE billing_origin_product = 'SQL'.
    Join to the latest row of a slowly changing tablewarehouses, clusters, instance_pools, jobs, job_tasks, pipelines, served_entities and alerts add a new row for each configuration change. This design is a slowly changing dimension. If you join to all rows, each usage row is counted once for each change, and your totals are too high. Keep one row for each object first, for example QUALIFY ROW_NUMBER() OVER (PARTITION BY workspace_id, warehouse_id ORDER BY change_time DESC) = 1. Add WHERE delete_time IS NULL only when you want objects that still exist.
    Use SUM to include billing correctionsDatabricks can correct usage rows later. A RETRACTION row has a negative quantity that cancels the original row. A RESTATEMENT row has the corrected quantity. Always aggregate with SUM(usage_quantity), so the corrections cancel out correctly.
    Use dot notation for struct fieldsWrite the full path to the field in the join, for example u.usage_metadata.warehouse_id = w.warehouse_id.
    Set skipChangeCommits = true when you streamA stream reads new rows from a table continuously. Databricks sometimes deletes rows from system tables, and these deletes can stop the stream with an error. This option tells the stream to ignore deletes and updates.

    Summary

    • System tables are in the system catalog. Unity Catalog controls access to them. You can read them, but you cannot change them.
    • Global tables, such as system.billing.usage and system.billing.list_prices, contain data from all regions. Regional tables, such as system.compute.* and system.query.history, contain data from the region of the current metastore only.
    • For cost and usage analysis, start with four schemas: billing, compute, query and access.
    • To read system tables, your workspace must use Unity Catalog. Users who are both account admins and metastore admins can read them by default. Other users need three grants: USE CATALOG on the system catalog, and USE SCHEMA and SELECT on the system schemas.
    • Filter on a date column first. Use billing_origin_product = 'SQL' to isolate SQL warehouse cost. Use SUM(usage_quantity) to include billing corrections.
